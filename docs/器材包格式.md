# 器材包格式

器材包是一个 **JSON 文件**，用来往小墨实验室里添加新器材。

它之所以安全，是因为包里的内容**全是数据**：没有脚本、没有 `eval`、
没有 `import`、不需要解压。每件器材都必须声明自己派生自哪件已有器材
（`proto`），渲染、电路特性、物理化学耦合这些行为**全部继承原型**，
你只能覆盖名称、外观尺寸、端口、默认参数和可调字段。

换句话说：**器材包改不了程序，只能配置程序。**

---

## 最小示例

```json
{
  "format": "xiaomo.equipment.pack",
  "version": 1,
  "id": "demo.pack",
  "name": "演示器材包",
  "author": "你的名字",
  "desc": "一句话说明这个包是干什么的",
  "equipment": [
    {
      "type": "demo-big-battery",
      "proto": "battery",
      "name": "大号干电池",
      "desc": "电动势更高的干电池，内阻也更大",
      "icon": "🔋",
      "defaults": { "emf": 9, "internalR": 1.2 }
    }
  ]
}
```

保存成 `任意名字.xiaomo-pack`（或 `.json`），然后从
**📦 器材包 → 导入器材包…** 装进去，左侧器材面板立刻就能看到它。

---

## 顶层字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `format` | ✅ | 固定为 `"xiaomo.equipment.pack"`，写错会被拒绝 |
| `version` | | 目前是 `1` |
| `id` | ✅ | 包的唯一标识，建议用 `作者.包名` |
| `name` | | 显示在器材包列表里的名字 |
| `author` | | 作者 |
| `desc` | | 一句话说明 |
| `equipment` | ✅ | 器材数组，至少一件 |
| `sha256` | | 可选的内容声明，用来核对内容没被改动过（见下） |

## 器材字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `type` | ✅ | 器材唯一标识，不能和已有器材重名 |
| `proto` | ✅ | 派生自哪件已有器材，必须是已注册的类型 |
| `name` | | 面板上显示的名字，不填就用原型的 |
| `desc` | | 面板上的说明文字 |
| `icon` | | 一个 emoji 或字符 |
| `domain` | | `physics` / `chemistry` / `bridge`，不填继承原型 |
| `cat` | | 面板里的分组标题，如「电源」「玻璃器皿」 |
| `tags` | | 字符串数组，用于搜索 |
| `w` / `h` | | 画布上的宽高（像素） |
| `ports` | | 接线柱数组，见下 |
| `defaults` | | **最常用**：覆盖可调参数的初始值 |
| `state` | | 覆盖初始运行状态 |

### 字段类型也会被检查

`name` / `desc` / `icon` / `domain` / `cat` 必须是字符串，`tags` 必须是字符串数组，
`w` / `h` 必须是正数，`ports` / `fields` 必须是数组，`defaults` / `state` 必须是对象。
类型写错会带着字段名被拒绝，比如把 `w` 写成 `"152"`：

> 器材「大号干电池」的 w 应该是正数，收到 string

**不认识的字段一律放行**（当作没看见，不影响导入）—— 这样以后给格式加字段时，
旧版本不会因为多了一个键就把整包拒了。

### ports（接线柱）

不填就继承原型的接线柱。填了会整体替换：

```json
"ports": [
  { "id": "pos", "x": 0.9, "y": 0.5, "polarity": "+" },
  { "id": "neg", "x": 0.1, "y": 0.5, "polarity": "-" }
]
```

`x` / `y` 是相对器材左上角的**归一化坐标**（0~1）。
每个接线柱都要有 `id`，`x` / `y` 必须是 0~1 的数字，否则整包被拒。

## 派生是「继承 + 覆盖」

派生出来的器材和原型**完全等价**，只是换了几项配置：

- 原型能导电 → 派生品也能导电，一样进电路求解
- 原型是容器 → 派生品也是容器，`capacity` 改掉即可
- 原型参与电解 → 派生品照样产氢产氧
- 原型能被烧坏 → 派生品照样受损坏规则约束

所以「500 mL 的宽口烧杯」不需要写一行代码：

```json
{
  "type": "wide-beaker",
  "proto": "beaker",
  "name": "宽口烧杯",
  "w": 92,
  "h": 84,
  "defaults": { "capacity": 500 }
}
```

## 内容声明 `sha256`（可选）

给包加一行 `"sha256": "…"`，导入时会现场核对：**对不上就整包拒绝**，并同时给出声明值和实际值。

它换来的是**完整性** —— 这一份内容和你以为的那一份一模一样：
复制粘贴被截断、编辑器「格式化」改坏、包被别人动过，都能当场发现。

但它**不是真实性**：本地文件导入没有签名，所以它证明不了作者是谁，
也证明不了这个包来自「可信来源」。包里的内容全是数据、改不了程序，
所以这条声明不是安全边界，只是「我装的这一份，就是我以为的那一份」。

- 算法：把 `equipment` 数组**规范化**（对象键名递归排序、去掉多余空白）之后，
  按 UTF-8 取 sha256，写成 64 位小写十六进制。键的顺序、缩进、换行都不影响结果，
  所以重新排版你的 JSON 不会让声明失效。
- 怎么拿到这个值：**📦 器材包 → 导出示例**，导出文件里那行 `sha256` 就是这么算出来的；
  也可以用同一套算法自己算：

  ```js
  const m = await import('/src/plugins/system.pack.js');
  m.contentFingerprint({ equipment: [ /* 你包里的器材数组 */ ] })
  ```

- 不写这一行完全可以 —— 软件在安装时自己还会记一份指纹，见下一节。

## 重开软件时会核对指纹

安装时软件会照上面的算法把内容算一遍，把指纹记在包的记录里（`_fp`）。之后每次启动装载时都核对：

- 一致 → 照常装回来；
- 不一致（记录被手改过、存盘被写坏）→ **不装载**，但**记录保留**，
  在 📦 列表里标出「校验不通过」和具体原因 —— 绝不静默丢掉你的数据；
- 早期版本装的包没有这个字段 → 自动补上，不会因为升级而集体失效。

> `_fp` 是软件自己写的。手改 `localStorage` 让它对不上，只会让这个包不被装载。

## 会被拒绝的情况

导入时会逐条检查，**任何一条不过就整包拒绝**（不会装到一半留下半套器材）：

| 情况 | 提示 |
| --- | --- |
| 不是 JSON 对象 | 不是一个 JSON 对象 |
| `format` 写错 | 不是小墨器材包（format 应为 …） |
| 没有 `id` | 缺少包标识 id |
| `equipment` 为空 | 包里没有任何器材 |
| 器材缺 `type` | 第 N 件器材缺少 type |
| 包内 `type` 重复 | 器材标识「…」在包里重复出现 |
| 器材缺 `proto` | 器材「…」缺少 proto |
| `proto` 指向不存在的类型 | 器材「…」引用了不存在的原型「…」 |
| `type` 和已有器材重名 | 器材标识「…」已被占用 |
| `version` 不是正整数 | version 应该是正整数 |
| `version` 比当前软件新 | 这个包用的是格式版本 v…，当前软件只懂 v… |
| 字段类型不对（如 `w` 写成 `"152"`） | 器材「…」的 w 应该是正数，收到 string |
| `tags` 里有非字符串 | 器材「…」的 tags 应该是字符串数组，收到 数组 |
| `ports` 里缺 `id`，或 `x` / `y` 不是 0~1 | 器材「…」的第 N 个接线柱 … |
| `fields` 里缺 `k` | 器材「…」的第 N 个可调字段应该是带 k 的对象 |
| `sha256` 不是 64 位小写十六进制 | sha256 必须是 64 位小写十六进制 |
| 声明的 `sha256` 与实际内容对不上 | 声明的 sha256 与实际内容不一致：声明 …，实际 … |

检查顺序：是不是 JSON 对象 → `format` → `version` → `id` → 顶层字段类型 →
声明的 `sha256` → 逐件器材（`type` / `proto` / 重名 → 字段类型 → `ports` / `fields` 形状）。
所以声明对不上时会先报声明，而不会先去挑器材结构。

同一个 `id` 的包重复导入时，会**先卸掉旧版本再装新的**，
所以修改器材包之后直接重新导入即可，不用先手动卸载。
（同一个包自己上一版贡献的类型不算「重名」，不会被自己的旧条目挡住。）

## 卸载

在 **📦 器材包** 里点对应包的「卸载」，包里的器材会从面板消失。
已安装的包记录在 `localStorage['xiaomo.packs.v1']`（其中含软件自算的指纹 `_fp`），
重开软件会自动装回来；指纹对不上时它不会装载，但会在列表里标明原因，记录也不会被丢掉。

> 如果场景里已经摆了某件器材、而它的包被卸载了，那件器材会读不出来。
> 卸载前先清空实验台比较稳妥。
